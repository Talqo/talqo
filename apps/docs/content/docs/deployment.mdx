## Docker Compose

The recommended way to run Talqo is the [talqo-deploy](https://github.com/Talqo/talqo-deploy) repository. It starts Talqo, Postgres, and Docling together as one Compose project. The Talqo image serves the dashboard, the widget, and the API from a single origin, so no CORS configuration is needed.

Clone the repository and start the stack:

```sh
git clone https://github.com/Talqo/talqo-deploy.git
cd talqo-deploy/docker-compose
cp .env.example .env
```

Then edit `.env` before the first start, because Talqo refuses to boot on the placeholder secret:

```sh
docker compose up -d
```

Talqo applies its own database migrations on start, so there is no separate migration step. The dashboard is on [http://127.0.0.1:3000](http://127.0.0.1:3000).

| Variable            | Default  | Purpose                                                         |
| ------------------- | -------- | --------------------------------------------------------------- |
| `TALQO_VERSION`     | `latest` | Image tag. Pin a specific version such as `0.1.0` to hold still |
| `TALQO_PORT`        | `3000`   | Host port, bound to loopback only                               |
| `APP_SECRET`        | None     | Required. Encrypts stored provider credentials, see below       |
| `POSTGRES_PASSWORD` | None     | Required. Must use URL-safe characters, see below               |

The port binds to `127.0.0.1`, so Talqo is reachable only from the machine it runs on. Put a reverse proxy on that host to terminate TLS and expose it. Setting `host_ip` in `compose.yaml` changes the binding, but do not publish Talqo to the internet without TLS in front of it.

Upgrades are a pull and a restart:

```sh
docker compose pull
docker compose up -d
```

Migrations are not reversible, so tracking `latest` means each pull can change your database schema. Take a database dump first, or pin `TALQO_VERSION` to decide exactly when that happens. Never run `docker compose down -v`: it deletes both named volumes, the database and the uploaded files.

`POSTGRES_PASSWORD` must be set once and then never changed. The Postgres image only reads it while initializing an empty data directory, so the stored role keeps its original password and changing the value in `.env` locks Talqo out of its own database.

## Application secret

Set `APP_SECRET` before running database migrations or starting the API. The API refuses to boot without it. It must be base64url-encoded and decode to at least 32 random bytes:

```sh
openssl rand -base64 32 | tr '+/' '-_' | tr -d '='
```

Back up this value separately from the database. Provider credentials stored through **Dashboard → AI configuration** are encrypted with a key derived from `APP_SECRET`; changing or losing it makes them unusable, and they must be entered again. Sessions survive a change, since session tokens are hashed without the secret, but rate limit counters reset.

## End-user chat policy

| Variable                                       | Default  | Purpose                                                                |
| ---------------------------------------------- | -------- | ---------------------------------------------------------------------- |
| `TALQO_CHAT_DAILY_MESSAGE_LIMIT`               | `100`    | Accepted questions per agent and normalized client network per UTC day |
| `TALQO_CHAT_MAX_CONCURRENT_GENERATIONS_PER_IP` | `2`      | Active generations per agent and normalized client network             |
| `TALQO_CHAT_MAX_INPUT_CHARACTERS`              | `400000` | Unicode code-point limit for the complete model input                  |
| `TALQO_CHAT_MAX_OUTPUT_TOKENS`                 | `16384`  | Provider output ceiling                                                |
| `TALQO_CHAT_GENERATION_TIMEOUT_SECONDS`        | `120`    | Model-call timeout in seconds, up to `300`                             |
| `TALQO_TRUSTED_PROXY_CIDRS`                    | Empty    | Comma-separated proxy networks whose forwarding metadata is trusted    |
| `TALQO_RATE_LIMIT_IPV6_PREFIX_LENGTH`          | `64`     | IPv6 network prefix used for allowance and concurrency identity        |

The API rejects invalid values at startup. These controls apply per agent/network, not deployment-wide, and do not implement billing or token quotas.

Configure `TALQO_TRUSTED_PROXY_CIDRS` only for proxies that actually terminate client connections. With no trusted proxy CIDRs, Talqo uses the direct peer address and ignores forwarding headers. Native IPv6 clients share a `/64` by default; this resists temporary-address churn but can make visitors on the same network share an allowance. A narrower grouping such as `/128` reduces sharing and increases bypass risk.
