The SDK connects your own chat interface to Talqo. It uses the same embed token, agent configuration, and server-side limits as the [pre-built widget](/embed-chat-integration).

## Install

```sh
npm install @talqo/sdk
```

The package includes browser ESM JavaScript and TypeScript declarations. Use it from a browser application with a bundler. Install the SDK version matching your Talqo server release.

## Connect your interface

Create an embed in the dashboard and copy its public token. Use your Talqo origin as `apiUrl`; do not include `/api`.

```ts
import { createChatClient } from "@talqo/sdk"

const chat = createChatClient({
	apiUrl: "https://talqo.example.com",
	embedToken: "YOUR_EMBED_TOKEN",
})

const unsubscribe = chat.subscribe(() => {
	const state = chat.getSnapshot()
	// Render state.messages and state.activity in your interface.
	console.log(state)
})

await chat.initialize()
await chat.sendMessage("What delivery options do you offer?")

// When your interface unmounts:
unsubscribe()
chat.dispose()
```

`initialize()` loads the embed configuration and restores the conversation. Subscribe before initializing so your interface observes loading and recovery states. `sendMessage()` streams updates through the subscription and resolves when sending completes. Catch rejected operations and render `getSnapshot().error` when present. Server-reported error codes are documented in the [API problem types](/problems) catalog.

## State and controls

`getSnapshot()` returns messages, configuration, activity, available actions, notices, active tool calls, and any error. Use `isAvailable` to hide an unavailable chat and `actions` to enable `send`, `stop`, `retry`, and `new-chat` controls. The SDK owns lifecycle and recovery decisions. `acceptedMessageId` identifies the latest accepted user message, so a UI can clear its submitted draft without inspecting transcript changes.

Render each message's `parts` in order. Text parts contain `text`. A `dynamic-tool` part contains the call, result, state, and `toolMetadata`. The metadata records the display name, source, server name when applicable, and outcome. `step-start` parts separate model steps and need no visible row. The message's `text` field concatenates text parts for previews. Render text as text or sanitized Markdown, never as unchecked HTML.

Use `cancelResponse()` to stop a reply, `retryLastMessage()` to retry after a failed response, and `startNewChat()` to clear the current conversation and begin another. `error.newChatAvailable` includes SDK recovery defaults when the server omits guidance. An explicit server value, including `false`, takes precedence.

The SDK stores conversation credentials in browser local storage and falls back to memory if storage is unavailable. A `storage-unavailable` error or notice means a reload can lose the conversation. The SDK owns streaming, cancellation, and reconnect recovery; custom interfaces should render its state rather than implement a second transport.

The pre-built widget tells end users that administrators may review the chat. Show an equivalent notice in your interface before the end user sends a message.

The embed token is public. Provider API keys and operator credentials must stay on the Talqo server.

## Browser tools

The agent's website-action setting enables the SDK's page tool, which observes and operates website controls. The agent decides when to ask for approval using the operator's saved instructions. The SDK waits for the visitor when the agent requests approval; it cannot identify every consequential website action on its own. The SDK owns the on-page action feedback, approval buttons, and Stop control. Custom interfaces do not render approval state.

Custom interfaces opt in by passing their chat's root element through `pageControl: { exclude: [chatElement] }` in `createChatClient()`. The tool cannot read or operate those roots. Without this option, ordinary chat and custom tools are unchanged. The pre-built widget supplies its root automatically. If browser tab storage is unavailable, website actions are disabled but chat remains usable.

To match the page controls to a custom UI, supply `pageControl.themeRoot: () => themedElement`. The controls follow that element's `--talqo-primary-input`, `--talqo-text-on-primary-input`, `--talqo-background-input`, `--talqo-surface-input`, and `--talqo-text-input` CSS properties, including style and class changes. The pre-built widget supplies its active palette automatically and remembers its open/closed state per embed across page loads when local storage is available.

The page tool continues across same-origin page loads in the same tab. Talqo must be installed on each destination page, and browser tab storage must be available. Reconnect within 20 seconds and before the original reply deadline; approval waits do not extend either limit. An API restart interrupts the task. Other origins, new tabs, and visitor-only payment steps require visitor participation. An interrupted action is inspected, never automatically repeated.

You can also pass ordinary AI SDK function tools when creating the client:

```ts
import { createChatClient } from "@talqo/sdk"
import { tool } from "ai"
import { z } from "zod"

const tools = {
	readPageTitle: tool({
		description: "Read the current page title",
		inputSchema: z.object({}),
		execute: async () => ({ title: document.title }),
	}),
}

const chat = createChatClient({
	apiUrl: "https://talqo.example.com",
	embedToken: "YOUR_EMBED_TOKEN",
	tools,
})
```

Install `ai` and your schema library alongside the SDK. Tools support `type: "function"`, a static `description`, `inputSchema`, `outputSchema`, `strict`, static `inputExamples`, and `execute`.

Talqo rejects other Tool API features, including AI SDK approval fields, provider-defined tools, callbacks, custom context, and streaming outputs. `execute` receives the AI SDK call ID, public conversation messages, and abort signal. Its `messages` exclude private instructions and retrieved knowledge-base context.

Register at most 8 tools in total. The page tool takes one slot when enabled. If all 8 slots are in use, chat keeps the registered tools and skips website actions. `talqo_page` is reserved for the page tool. Turns with the page tool allow 64 browser-tool calls; other turns allow 16, including failures. Provider steps retain the ordinary limit until the model actually calls the page tool. Inputs and outputs must be JSON values of at most 256 KiB each. The tool manifest is limited to 128 KiB. The SDK validates inputs and declared outputs locally.

Talqo stores browser and MCP tool results in conversation history and sends them to the model on later completed turns. Do not return secrets or unnecessary personal data.

Website observations include visible page text and ordinary form values. They are sent to the configured AI provider and retained in conversation history, where operators can review them. The tool skips iframes and password fields and uses field attributes to identify other sensitive controls. It cannot detect every sensitive value. Exclude sensitive page sections through `pageControl.exclude`, even if the fields look like ordinary inputs. Reported page URLs omit query strings and fragments. Approval summaries are model-written proposals, not verified transaction receipts; the website remains the source of order details.

Browser tools run with your page's permissions. Register only actions you intend the agent to perform, validate application permissions inside `execute`, and honor its abort signal. Stopping or disconnecting cannot undo an action already performed. Interrupted calls are never replayed automatically. When `website-action-uncertain` is reported, tell the visitor to check the page before repeating an instruction.

Live turns require WebSocket access to the Talqo origin. See [Deployment](/deployment) for proxy requirements.
